# Integration Test Cases: TB-1860 — Idempotency (duplicate prevention) — v5

Source: v4 + a full Bruno verification pass (`C:\Users\user\BrunoApi\proj-bruno-api`, the
authoritative API contract per `docs/frame-specs/api-conventions.md`) against every endpoint,
schema, and payload shape used in this suite's Product Factory, Validation Engine, Field Registry,
and Table Registry cases. **This pass found real, concrete field-naming errors in v4 — corrected
below, not silently patched.**

## Bruno Verification & Corrections

### 1. Product Factory field names use underscores, not dots — confirmed from the real schema-seeding requests

Read directly: `Tables/Product Factory/00 - Seeding/05 - Update Schemas/{04,05,06,07,08,09}
Update PF.*.yml` (the actual `PUT tables/api/v1/tables/PF.*/definitions` bodies this platform's
own seeding uses). **Confirmed field map** (properties only — `ID`/`DESCRIPTION` omitted per row
since every one of these tables has them identically: `ID` ALPHANUMERIC, `DESCRIPTION`
MULTILANGUAGE_TEXT object `{"en": "..."}`):

| Table | Real fields (beyond `ID`/`DESCRIPTION`) |
|---|---|
| `PF.CLASS` | `ATTRIBUTE_CLASSES` (array of `{ATTRIBUTE_CLASS, MANDATORY}`) |
| `PF.TYPE` | `PRODUCT_CLASS` (linked to `PF.CLASS`), `ATTRIBUTE_CLASSES` (array of `{ATTRIBUTE_CLASS, ATTRIBUTE, MANDATORY}`) |
| `PF.BUILDER` | `PRODUCT_TYPE` (linked to `PF.TYPE`), `PARENT_PRODUCT`, `PRODUCT_CURRENCIES` (array), `ATTRIBUTES` (array of `{ATTRIBUTE, CONDITION, EFFECTIVE_AFTER, CONTRACT_LINK_TYPE}`) |
| `PF.PRODUCT` | Same as `PF.BUILDER` plus `PRODUCT_STATUS` (enum), `LAST_CATALOGED`/`AVAILABLE_DATE`/`EXPIRY_DATE` (DATE) |
| `PF.MANAGER` | `ACTION` (enum `VALIDATE`/`CATALOG`, **no `ID`/`DESCRIPTION`**), `COMBINE_ACTIONS` (**boolean**), `PRODUCT_STATUS`, `ACTION_ERRORS` (array), `RESOLVED_CONDITIONS`, `AVAILABLE_DATE`, `EXPIRY_DATE` |
| `PF.CATALOG` | `STATUS` (enum `CATALOGED`/`EXPIRED`), `RESOLVED_CONDITIONS`, `PRODUCT_VERSION`, `PRODUCT_TYPE`, `AVAILABLE_DATE`/`EXPIRY_DATE`, `PRODUCT_CURRENCIES` |

**This repo's own `test-data/payload-builder.ts`** (`buildPfTypePayload`, `buildProductPayload`,
`buildManagePayload`) uses the **old dotted convention** (`'PRODUCT.CLASS'`, `'COMBINE.ACTIONS'`
as a *string* `"true"`/`"false"`) — this is a real discrepancy between this repo's own test helper
and the platform's actual current schema, worth flagging to the AQA Lead separately (it may affect
other, already-existing Product Factory tests that rely on these builders, not just this ticket).
**Every v5 case below uses literal bodies with the Bruno-confirmed field names instead of citing
those stale builder functions.** Note: dots are still correct in **ID/record values** (e.g.
`"PERSONAL.LOANS"`, `"CARLOAN_123"` are real seeded business identifiers) — the error was applying
dots to *field/property names*, not record IDs.

### 2. `PF.MANAGER`'s `INPUT` acts on an *existing* product, not a fresh independent record

Confirmed via `Tables/Product Factory/00 - Seeding/12 - Full Lifecycle E2E Test/`: step 1 creates a
`PF.BUILDER` draft with a generated `recordId`; step 3 (`VALIDATE plus CATALOG`) calls `PF.MANAGER`
`INPUT` with **the same `recordId`** — `PF.MANAGER` validates/catalogs a product that already
exists, it does not create one from scratch. Every v5 case anchored on `PF.MANAGER` now creates a
`PF.BUILDER` draft first, in its own first numbered step, reusing that same `recordId`.

### 3. Validation Engine (`Create Rule`) and Field Registry (`Create field`) — reconfirmed unchanged

`POST tables/api/v1/projections/:projectionId/rules` with body `{name, origin, result:{type,id},
condition:{key,operator,values}}`, and `POST field-registry/api/v1/fields` with body `{id, title,
type, config, origin}` — both exactly match what v4 already used; no case needed a contract fix
here. Tightened one stylistic inconsistency: the one case that named its custom Validation-Engine
field `AMOUNT` now uses `transaction_amount`, matching this repo's own established Validation
Engine test convention (`getValidationEngineTestSchema()` in `projection-helper.ts`) instead of an
inconsistent one-off.

### 4. Date field naming — corrected

v4's date-normalization case (`BR-3.5`) referenced a vague `EFF_DATE` field name that does **not**
appear anywhere in the confirmed Bruno schema. The real, confirmed date fields are `AVAILABLE_DATE`
/ `EXPIRY_DATE` / `LAST_CATALOGED` (top-level DATE fields on `PF.PRODUCT`/`PF.CATALOG`) — `v5`
reanchors this case on `PF.PRODUCT`'s real `AVAILABLE_DATE` field instead.

### 5. Everything not listed above is unchanged from v4

Table Registry (Groups/Tables), RBAC (`SM.USER.GROUP~MAIN`), the `/accept` continuation endpoint,
Units 4–5 (COB/Party Merge, still design-only) — all already verified against real repo code or
Bruno in earlier passes; nothing new to correct there.
