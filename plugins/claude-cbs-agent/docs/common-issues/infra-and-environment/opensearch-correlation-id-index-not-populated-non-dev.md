# OpenSearch correlation-id field confirmed, but non-`dev` env indices appear empty (open, 2026-09-24)

**Confirmed (2026-09-24, via the platform/backend developers):** `proj-correlation-id-starter`
does log the inbound `X-Correlation-ID` header, under OpenSearch field **`app.correlationId`**, on
index pattern **`proj-<env>`** (e.g. `proj-dev`). Discover link shape:
`http://opensearch.proj.local/app/data-explorer/discover#?_a=(discover:(columns:!(app.correlationId),...),metadata:(indexPattern:proj-<env>,view:discover))`.
This resolves the "not a confirmed mapping" caveat previously carried in
`docs/frame-specs/api-conventions.md`'s `X-Correlation-ID` row — the field name is now known.

**Open issue, not yet root-caused:** querying `proj-stg` for a correlation id generated by a real
`bankstg` test run (`0ccd9e46-2163-4077-8af8-bc91e5cab9f5`, `api/system_core/tests/customization-smoke.spec.ts`,
`table-registry` service, 2026-09-24 10:16:29 UTC) returned nothing — and separately, `proj-stg` (and
every env except `proj-dev`) appeared to have **no recent logs at all**, not just missing this one
field. `proj-uat` was NOT empty. `proj-correlation-id-starter` was reportedly merged ~3 weeks before
this date, "should already be there" per the platform developer, who suspected index templates/mappings not
deployed to non-`dev` OpenSearch clusters and was going to check further (left mid-investigation,
2026-09-24 lunchtime — not yet confirmed root cause or fix).

**Why this matters for AQA work:** before concluding a test failed to send `X-Correlation-ID` (or
any other header) because it can't be found in OpenSearch on `stg`/other non-`dev` envs, first
confirm that env's `proj-<env>` index has *any* recent data at all — an empty index was the default
state for most non-`dev` envs as of this date, independent of whether the client actually sent the
header correctly. In the incident that surfaced this, the test-side propagation
(`testCorrelationId` fixture → `authenticatedApiContext` → request headers) was independently
verified correct via the Allure result and code review before this OpenSearch gap was found — don't
default to "the test framework didn't send it" when the simpler explanation is "the log pipeline
for this env isn't wired yet."

**Not a `proj-test-automation` code issue** — this is a platform/OpenSearch-provisioning question,
follow up with the backend/platform team for the actual root cause.
