## Entries

- [`delegation-not-self-applied.md`](delegation-not-self-applied.md) — having `base-agent.md`/`model-routing.md`'s Gather-stage delegation rule loaded doesn't guarantee it gets applied before reaching for `Bash`/`Read`/`Grep`; now backstopped by `hooks/delegation-track.ps1` + `hooks/delegation-check.ps1`, same pattern as the Task Closeout hooks.
- [`two-proj-ai-agentic-clones-resolver-picks-real-one.md`](two-proj-ai-agentic-clones-resolver-picks-real-one.md) — a machine can have `proj-ai-agentic` checked out in more than one place (the user's real dev clone vs. Claude Code's own marketplace-managed mirror); always resolve the real tree via `Resolve-CbsAiAgenticRoot`'s own algorithm before editing, never assume a path reached via an unrelated diagnostic is the same tree the user pushes from.
- [`shared-helper-used-outside-migration-scope.md`](shared-helper-used-outside-migration-scope.md) — before editing a shared helper as part of the TB-3587 migration, grep every caller across the whole `api/` tree; a helper used by an out-of-scope module (Audit Fields, Enquiry) needs a new parallel function, not an in-place edit, and "imports test-user-service + no direct USERS_DATA" doesn't prove a spec is fully migrated if it still calls an unmigrated shared helper (`system_core`, 2026-09-04). Counter-example: a shared helper that only accepts an already-built context (a setter, not a builder) is safe to leave alone — migrate each caller's own construction code instead (`customer`, 2026-09-04).
- [`fork-executed-literal-git-commands-from-a-read-plan-doc.md`](fork-executed-literal-git-commands-from-a-read-plan-doc.md) — a fork told to read a planning doc "for context" executed the literal `git add`/`git commit` steps embedded in it, producing an unauthorized commit (19 already-reviewed files + 3 unrelated shared-framework files bundled in); a scoped `git diff --stat -- api/<module>/` after a fork doesn't catch this — always also check `git status`/`git log -5` for the whole repo (TB-3587, 2026-09-07).
- [`merge-conflict-resolution-diff-size-strategy.md`](merge-conflict-resolution-diff-size-strategy.md) — before resolving a merge conflict hunk-by-hunk, compare `git diff <merge-base> HEAD` vs `git diff <merge-base> MERGE_HEAD` for that file; a dramatically larger incoming diff means the other side did far more work than the conflict markers alone show (unmarked regions can silently differ too) — rebuild from the bigger side and reapply the smaller diff, checking first whether the bigger side already fixed the same problem differently. Also: a non-conflicting new file that fails to compile after a merge can be broken by *our own* branch's history (a legitimate deletion that predates the other side's new file), not necessarily "pre-existing main breakage" — verify provenance with `git show MERGE_HEAD:<path>`/`git log -p -- <path>` before asserting whose fault it is (TB-3587, 2026-09-07).
