## Entries

- [`unchecked-precondition-response-masks-root-cause.md`](unchecked-precondition-response-masks-root-cause.md) — a helper's earlier API call in a chain must be checked before a later dependent call, or the earlier call's real failure surfaces as a confusing symptom on the later one instead.
- [`shared-record-snapshot-restore-race-under-concurrency.md`](shared-record-snapshot-restore-race-under-concurrency.md) — `SEE`-capture-mutate-restore on a shared/singleton record (e.g. `COMPANY`) races under concurrent test execution and can leave a permanently dangling reference that blocks every future update to that record, even on later unrelated single-process runs; sanitize referenced entities in the captured snapshot before reusing it.
- [`raw-db-bypass-of-immutable-field-caused-qa-outage.md`](raw-db-bypass-of-immutable-field-caused-qa-outage.md) — `ensureSystemShareCusData`/`clearSystemParameterInDb` `DELETE`+recreate a singleton row via raw SQL to force a value the API rejects with 400 — but the repo's own regression suite (TC-18, Allure 459) proves that 400 is a deliberate "immutable field" rule, not a bug; a human "fixing" the same 400 by hand in DBeaver against `proj_qa` caused a real outage, 2026-09-03.
- [`db-helper-reconnect-race-hangs-client.md`](db-helper-reconnect-race-hangs-client.md) — `createDbClient()`'s `reconnect()` wasn't serialized: a keepalive ping and a real test query hitting a connection error at the same moment could both independently reconnect and race on the shared `current` client, leaving it in a state where a later `.query()` never resolves (hangs forever, no error) instead of throwing; fixed with an in-flight-reconnect guard so concurrent callers await one shared reconnect (2026-09-04).
- **Parallelization readiness audit (2026-09-16)** — `resource-tracker.ts`'s `untrackUser`/`untrackTables` did a `readFileSync`→filter→`writeFileSync` against the shared `test-results/tracked-resources.jsonl`, called from per-test cleanup, not just global teardown; this was a genuine cross-process race once `workers` > 1 (last writer wins, dropped untrack entries → orphaned resources or double-delete). **Fixed same day**: both functions now append an `untrack-table`/`untrack-user` tombstone line instead of rewriting the file (same atomic-append pattern already used by `trackCreated*`); `getTrackedResources()` reconciles tombstones against creates at read time (called only once, from global-teardown, in a single process — so the reconciliation itself has no race). Full audit incl. shared-identity and singleton-record risks: `docs/frame-specs/parallelization-readiness.md`.
- [`cleanup-failure-swallowed-by-caller.md`](cleanup-failure-swallowed-by-caller.md) — a helper's own success/failure return value discarded by its caller (`cleanupGroupById`'s API-delete result ignored, so `cleanupStaleGroups` logged "Successfully cleaned up" right after a `403`), and a docstring promising "aborts early" with no actual `throw` in the function body (`assertServiceReachable` in `global-setup.ts`, now fixed) — both closed 2026-09-07 (TB-3587). Follow-up same day: `cleanupStaleGroups` now trips a circuit breaker (`CLEANUP_CONSECUTIVE_FAILURE_THRESHOLD = 3`) on 3 consecutive per-group failures across *different* groups and aborts the whole sweep instead of grinding through every remaining stale group against a dead environment.
- [`stale-cross-run-data-triggers-duplicate-checks.md`](stale-cross-run-data-triggers-duplicate-checks.md) — leftover `TF.FUNDS.TRANSFER`/account records from runs hours-to-days old collided with real `funds-transfer-duplicate-check`/aggregate-balance assertions in a brand-new run (2026-09-18); prefer delta-based assertions over exact totals on shared/long-lived bankstg records. Also notes an unconfirmed cleanup double-delete pattern (table-group/Kafka-topic "already gone") seen in the same run.
- [`user-groups-never-swept.md`](user-groups-never-swept.md) — `SM.USER.GROUP~MAIN` records created by tests are only deleted per-test in `deleteTestUser` (response status never checked); no automatic pre-test sweep exists (manual: `npm run db:cleanup -- --scope user`), so two.bankuat held 4489 user groups (4201 test-owned) and bankuat 12074 on 2026-09-29; `TEST_OWNED_NAME_PATTERN` is also blind to `.`-separated ids.
