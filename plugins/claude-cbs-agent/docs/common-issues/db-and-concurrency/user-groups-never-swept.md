# User groups (`SM.USER.GROUP~MAIN`) are never swept — they accumulate by the thousands

## TL;DR

| | |
|---|---|
| Symptom | Thousands of test-created user groups on shared envs (2026-09-29: two.bankuat 4489 total / 4201 test-owned, 4054 older than 12h; bankuat 12074 / 11770) while table groups look clean (two: 50, 0 stale). |
| Root cause | The pre-test sweep (`cleanupOrphanedSchemas` + `cleanupStaleGroups`) only covers Table Registry table groups/tables. User groups are only deleted per-test in `deleteTestUser` (`test-user-service.ts`), which never inspects the `DELETE` response status (`performRecordOperation` returns the `APIResponse` without throwing on non-2xx), so a rejected delete is silently ignored; only a thrown error reaches `console.error`; killed/timed-out runs never reach it. |
| Rule | "Groups are cleaned before tests" is true for **table groups only**. Any new fixture that creates `SM.USER.GROUP` records needs its own reliable teardown or a sweep. |
| Status | 2026-09-29: (1) `deleteTestUser` now deletes via `deleteUserGroupChecked` — checks the DELETE result AND polls `sm_user_group.liv` until the id is gone, throwing (logged) otherwise; (2) a `global-setup` user-group sweep was added and then **removed the same day** (every DELETE returns 400 on two.bankuat, see below) — `global-setup` sweeps table groups/orphans only; (3) manual: `npm run db:cleanup -- --scope user`. Code in `api/system_core/helpers/user-group-cleanup-helper.ts`. Still open: groups referenced by leftover `SM.USER` profiles are never removed. |

## Details

- Big buckets on two.bankuat (id prefix): `aqa_aqa.user.group_w*` ~2950, `aqa_tc-lock-group` 268, `aqa_ovr_full_grp` 107, `AQA-NO-TR-DELETE` 89, `aqa_ovr_scope_grp` 89.
- `TEST_OWNED_NAME_PATTERN` (`/[-_]\d{13}|^qa[-_]|^pr[-_]|^aqa/i`) needs `-`/`_` before the timestamp, so `TEST.GROUP.PARTIAL.<13 digits>` (78) and `TEST.GROUP.WORKSPACE.MENU.*` are treated as not test-owned by every sweep. Same for legacy table groups `AAA-LOCAL-GROUP-<10 digits>` / `AAA-GROUP-HEAL-<10 digits>` (ids 4441/4443 on two).
- Unverified hypothesis (medium confidence): `deleteTestUser` deletes the user group *before* the Keycloak user/`SM.USER` profile that still references it, so CBS may reject the `DELETE`.
- Numeric ids and named groups (`SHOWCASE`, `REPORTING.ADMINS`, ...) are real, non-test data — a future sweep must not match them.
- Manual table-group/orphan sweep for a chosen env: `npm run db:cleanup` (see `frame-specs/infrastructure.md`).
- **Safety guard (2026-09-29):** on two.bankuat 3344 of 4140 name-matched stale candidates were still referenced by an existing `SM.USER` profile (`sm_user.liv`/`nau`, `GROUPS` field; 6052 profiles, mostly leftover test users, some persistent ones like `3b8a0b07-...` holding several groups). The manual sweep therefore skips any group referenced by a profile — name + age alone is not a safe test-vs-real criterion. Cleaning the leftover test profiles themselves is a separate, unbuilt step.

- **Live finding, 2026-09-29 (first run with the checked delete, two.bankuat):** every `SM.USER.GROUP~MAIN` `DELETE` — sweep candidates *and* the fresh per-test group in `deleteTestUser` — returned `400 {"detail":"DELETE operation cannot be performed for record id=<id>, seqNo=1", ...}` (body truncated in the log; error handler now keeps 600 chars). So on two.bankuat this projection's DELETE does not work at all, and `deleteTestUser` has been silently failing there all along (the root cause of the pile-up). This contradicts the proj-qa result in [`../test-user-service/test-user-service-group-cleanup-db-verified.md`](../test-user-service/test-user-service-group-cleanup-db-verified.md) (DELETE purged rows there, 2026-09-08) — behaviour differs per environment; reason for the 400 (projection config, e.g. authOperationRequired/seqNo state, vs. env difference) still to be read from the full response body. The sweep aborts after 3 failed batches, so it is harmless but noisy until DELETE works or another removal path is chosen.

- **Bruno check (origin/main, 2026-09-29):** `SM.USER.GROUP` has no `DELETE` request at all — only INPUT/SEE (table-template folder documents INPUT, SEE, HOLD, AUTH) and seeding requests; `SM.USER.GROUP~MAIN` is created with `authOperationRequired: false` (INT table, `spaces` include DEL). The `"DELETE"` strings found under that folder are just the permission `FUNCTION` enum inside a group's `PERMISSIONS` field, not an operation definition. In the repo every 200-asserting `DELETE` test acts on a pending draft (NAU/UNAU/HNAU/RNAU — e.g. table-registry-regression TC-068: INPUT → AUTH → REVERSE → DELETE removes the RNAU draft); a `400 ... cannot be performed for record id=X, seqNo=1` is what a record already sitting LIVE in `liv` with no draft gets. So our `DELETE` on a LIVE group is outside the documented contract; the supported removal path (if any) is unknown — needs a dev/BA answer. Payload `{ recordId }` matches every other call in the repo.

- **Developer answer (CBS backend developer, 2026-09-29):** `DELETE` works only for records in the NAU space. To remove a record from LIV the supported operation is `REVERSE` — it moves LIV → HIS, i.e. hides the record, it does **not** remove it from the database. Removing rows from HIS is only possible through the DB. Consequence: there is no API path that physically deletes a LIVE `SM.USER.GROUP~MAIN` record; physical cleanup of test groups = direct SQL on `sm_user_group.liv/nau/his` (guarded: test-owned id + timestamp older than threshold + not referenced by any `SM.USER` profile), and the per-test `DELETE` in `deleteTestUser` should become `REVERSE` (or be dropped in favour of the SQL sweep). Whether REVERSE on this `authOperationRequired: false` projection needs a second AUTH is not yet verified.

- **Implemented after the developer answer (2026-09-29, static checks only, not yet run live):** `deleteTestUser` now calls `reverseUserGroupChecked` (`REVERSE` on `SM.USER.GROUP~MAIN`, then polls `sm_user_group.liv` until the id has left LIV; a still-present group is reported with a hint that an AUTH may be needed — unverified whether this `authOperationRequired: false` projection needs one). `npm run db:cleanup -- --scope user` now physically removes stale unreferenced test groups via SQL from `liv`/`nau`/`his` (batched transaction, re-check of profile references right before deleting, post-delete existence check), and also finds groups that only exist in `his`/`nau` (already reversed). The API-`DELETE` sweep and the `global-setup` sweep were removed. Groups still referenced by leftover `SM.USER` profiles are never touched.
