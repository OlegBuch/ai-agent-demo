# common-issues/keycloak-and-auth/ — Keycloak login/lockout behavior and AUTH/permission-check gotchas

Part of `docs/common-issues/` — see the parent `docs/common-issues/INDEX.md` for the overall
cross-cutting-knowledge convention (when something belongs here vs. in a module folder, how to
add/update an entry, when to create a new file vs. extend an existing one).

## Entries

- [`auth-operation-required.md`](auth-operation-required.md) — before writing or copying an `INPUT`-then-`AUTH` call sequence, check the target projection's `authOperationRequired` flag; several tables (`SM.USER.GROUP~MAIN`, `SM.USER~INTERNAL`) have no AUTH stage at all, so an unchecked AUTH call after INPUT is a silent no-op `404`.
- [`keycloak-transient-login-401.md`](keycloak-transient-login-401.md) — Keycloak can reject a password-grant login as `401 Invalid user credentials` purely from load, not bad credentials; `withKeycloakLoginRetry` retries every failure class uniformly (3 attempts/8s) and the credential circuit breaker's trip threshold is tied to that same attempt count; the outer `create...ApiContextWithRetry` still doesn't re-retry a `KeycloakAuthError` on top of it. Also: Bruno's own admin-token request confirmed byte-identical to ours — a Bruno success / our-code failure at the same moment is the account's own intermittent state, not a request-shape bug (2026-09-04). **2026-09-17: a later merge (`1f606b2e`) had silently reintroduced the "never retry AUTH_INVALID_CREDENTIALS" exclusion this doc already documented as reverted — re-removed; if this recurs, `git log -S` the removed symbol before assuming a new bug.** **2026-09-17, later same day: live-verified at real N=3+1 on bankstg (retry alone handled it, no failures); added a complementary pre-login `.well-known` readiness probe + `TEST_PARALLEL_INDEX`-based login stagger (`ensureKeycloakRealmReady`/`staggerInitialKeycloakLogin`, `token-service.ts`) to reduce how often the burst happens at all — open question left on why the failing label was literally `proj-admin` rather than the per-worker super-admin.**
- [`transient-403-not-retried.md`](transient-403-not-retried.md) — `BaseApiClient`'s built-in retry for `"does not have access to table"` only fires on `status === 400`; a permission-propagation race on an AUTH call returns `403` instead, so the retry never triggers — fix scoped per-client via a custom `isTransientClientError`, never by broadening the global default (breaks legitimate persistent-403 negative-permission tests elsewhere).
- [`keycloak-shared-credential-lockout-and-ci-log-masking.md`](keycloak-shared-credential-lockout-and-ci-log-masking.md) — a module still falling back to the shared `KEYCLOAK_USERNAME`/`PASSWORD` (not yet migrated to per-test users) can genuinely lock that account under CI test volume; fixed with (1) a consecutive-failure-counted circuit breaker (trips after 3, not 1, and resets on success — a single trip was stricter than the realm's own lockout policy) that short-circuits repeat attempts once a credential is confirmed invalid, (2) a run-scoped "super-admin" bootstrap user (`global-setup`/`global-teardown`) that now stands in for `proj-admin` everywhere except its own create/delete calls — maker/checker/no-permission users unaffected, and (3) a fix to `createTestUser`'s own group-creation path, which was leaking one untracked `SM.USER.GROUP~MAIN` record per call for *any* caller using `options.permissions`, not just the super-admin. Separately, GitLab's "Masked variable" feature (not this repo's own logging) scrubs the username from CI logs too, defeating the identity-tagging fix — still needs a GitLab CI/CD Variables setting change to un-mask it (TB-3587, 2026-09-03/04). **2026-09-17: that one run-shared super-admin itself became a bottleneck at 2+ concurrent workers — Fix 6 made it per-worker (in-memory `workerSuperAdmin`, no more sentinel file) instead of per-run. Fix 7 (same day): the run-shared `DYNAMIC_GROUP_ID` table group had the identical shape and risked the (unenforced-client-side) `MAX_REUSABLE_GROUP_TABLE_COUNT: 10` cap under concurrent workers — made per-worker too, via the `workerGroupId` fixture itself creating/deleting the group instead of reading one `global-setup.ts` created.**
- [`authenticatedapicontext-already-covered-by-super-admin.md`](authenticatedapicontext-already-covered-by-super-admin.md) — the plain `authenticatedApiContext` fixture (no explicit username/password) already resolves through the super-admin bootstrap via `resolveKeycloakCredentials`, not `proj-admin`; a spec file using only that fixture (no `USERS_DATA`) doesn't need TB-3587 migration for the lockout-risk reason — that risk is already closed at the fixture layer (`system_core`, 2026-09-04).
- [`partially-access-user-standing-permission-resolved.md`](partially-access-user-standing-permission-resolved.md) — `PARTIALLY_ACCESS_USER`'s undeclared baseline grant (blocking TC-15/16/100/131's migration) was membership in an `SM.USER`-scoped group; a disposable user with `permissions: [{ TABLE: 'SM.USER', FUNCTION: 'ALL' }]` reproduces it, closing TB-3587's last open item (2026-09-07).
- [`keycloak-master-admin-creds-missing-on-bankstg.md`](keycloak-master-admin-creds-missing-on-bankstg.md) — a missing-env-var failure (`KEYCLOAK_ADMIN_USERNAME`/`PASSWORD`, a master-realm pair distinct from the service-account `KEYCLOAK_ADMIN_CLIENT_ID`/`CLIENT_SECRET` everything else uses) can mean the workaround needing it is now obsolete, not that the environment needs one more secret — check `git log -S` on the introducing commit before provisioning a new credential. Resolved by switching `customer-party-integration.spec.ts` back to the already-working service-account path and deleting the now-fully-unused `createMasterAdminKeycloakUser`/`deleteMasterAdminKeycloakUser`/`resolveMasterAdminKeycloakContext` (~95 lines, `auth-service.ts`) plus an unrelated dead `getUserKeycloakAccessToken` export found in the same sweep (e2e suite on Azure, 2026-09-07).
