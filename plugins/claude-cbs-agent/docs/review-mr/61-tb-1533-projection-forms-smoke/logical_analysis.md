# Logical Analysis — MR !61 (TB-1533: Projection Forms & UI Framework - Smoke)

## Summary

TB-1533 ("Test implementation: Projection Forms & UI Framework - Smoke", Highest priority, status
"In Code Review") asks for the smoke TC set for EP-01.06 ("Projection Forms & UI Framework") per
the linked Confluence spec and the Google Sheet TC list. The spec's smoke-relevant scope is
TRC-01..09 (Projection Definition Engine, field overrides, auto-defaulting, layout/grouping,
validation hooks, transaction governance, operations hooks, resolution waterfall, transaction
confirmation) with four Acceptance Criteria (AC-SCR-01..04: schema-on-read, override enforcement,
auto-defaulting, audit trail). The diff adds one large new spec,
`api/system_core/tests/projection-forms-smoke.spec.ts` (1225 lines, 10 `TC-<n>` cases tagged
`@smoke_m2`/`@api`), a brand-new `PluginManagerApiClient` + paths/values files (Plugin Manager was
previously unautomated per `docs/project-spec/domain-model.md`), a new `inputProjectionDefinition`
client method reusing an existing path constant, `postMultipart`/`putMultipart` additions to
`BaseApiClient` for JAR upload, a widened envelope-unwrap/list-extraction helper set in
`projection-helper.ts`, minor type-gap fixes, and a committed binary plugin JAR fixture. **Note on
diff scope**: this review verified MR !61's actual diff against `origin/HEAD` directly via `git
diff`/`git log` (independently, twice) — it touches exactly 17 files, 1977 insertions/16 deletions,
and does **not** touch `.gitlab-ci.yml`, `kafka-service.ts`, `kafka-health-check.spec.ts`,
`table-registry-helper.ts`, or `group-cleanup-helper.ts`; all of those already exist on `main`
(merged separately as TB-1354's Kafka CI/CD work, visible in this repo's own recent commit log).
Findings below are scoped strictly to the 17 files this MR's diff actually changes.

## Confirmed Issues

**[Confirmed] `afterAll` deletes the shared worker-scoped table group, breaking isolation for every other suite sharing it.** `projection-forms-smoke.spec.ts:201-202` assigns `testGroupId = workerGroupId` and immediately pushes it into `createdGroupIds`; `:236` / `:254-256` then unconditionally loops `createdGroupIds` and calls `cleanupClient.deleteGroup(groupId)` on it in `afterAll`. `workerGroupId` is documented in `api/utils/api-fixtures.ts:14-26` as a worker-scoped fixture explicitly "Reusing global table group ID" (`getDynamicGroupId() ?? TEST_CONSTS.GROUP_ID`) — a single shared resource meant to persist across every spec file in the run, not something an individual spec creates or owns. The sibling spec `api/system_core/tests/system-parameterization-smoke.spec.ts:48-51,82-85` reads the exact same `workerGroupId` and never deletes it, confirming the established convention this new spec breaks. Any other `@smoke_m2`/`@regression` spec sharing this group in the same CI worker/run will start failing with 404s on group-scoped operations once this spec's `afterAll` runs. Fix: never push `workerGroupId`-derived ids into `createdGroupIds`; only track/clean up a group this spec actually creates itself (it currently creates none).

**[Confirmed] Hand-rolled group/context cleanup duplicates the existing `cleanupGroupById` helper.** `projection-forms-smoke.spec.ts:236-279` builds its own `APIRequestContext`, instantiates a throwaway `TableRegistryApiClient`, and loops calling `.deleteGroup()` per group with manual try/catch logging — reimplementing, less completely, what `api/utils/group-cleanup-helper.ts:109-183`'s `cleanupGroupById()` already does in one call (DB metadata delete + schema drop + retried API delete + Kafka-topic cleanup via `deleteKafkaTopicsForTableIds`). This is the suite-wide duplication the AQA Lead lens is specifically responsible for catching. Fix: if a group genuinely needs deleting here (see the issue above — currently none should), call `cleanupGroupById` instead of reimplementing it inline.

**[Confirmed] TC-193's SEE-runtime hook/layout assertions only fire when the field happens to be present, so the test can pass without ever proving the AC it claims to cover.** `projection-forms-smoke.spec.ts:971-973` (`if (Array.isArray(executedHooks)) { expect(...).toBeGreaterThan(0); }`) and `:976-989` (layout/fields/schema checks, all gated the same way) never assert that `executedHooks`/`layout`/`fields` exist at all — if the backend omits them entirely (plausible given the adjacent "Failed - no Rules" annotation on this same test, line 861), the test still passes having verified nothing about hook execution (TRC-07) or runtime layout (TRC-04), the exact acceptance criteria Step 2-4 of this test exist to check. Fix: assert existence first (`expect(executedHooks).toBeDefined()` / `toEqual(expect.any(Array))`) before the conditional type checks, or split the currently-optional checks into their own tracked case if the backend genuinely doesn't return them yet.

**[Confirmed] Artificially widened `space` accepted-values list papers over a precondition this same test already resolved.** `projection-forms-smoke.spec.ts:960-968` accepts `['LIV', 'NAU']` for the runtime SEE response's `space`, with a comment allowing for "FIN maker-checker" behavior — but this suite's only table (`TABLE_ID`) is created with `classification: TEST_CONSTS.CLASSIFICATION.INT` (line 228), and TC-02's own assertion earlier in this same file already established "INT table first INPUT should create a LIVE record without AUTH" (`toBe('LIVE')`). The FIN branch can never apply here, so widening the accepted list to include it hides what should be a deterministic `'LIV'` assertion. Fix: assert `space` equals `'LIV'` directly, matching the classification this test itself fixes at setup.

**[Confirmed] Five smoke test cases carry unresolved "Failed"/"Blocked" defect markers with no quarantine, inside the exact tag this MR's own CI job runs on every future MR.** `projection-forms-smoke.spec.ts:282` (TC-48), `:386` (TC-106... comment reads "Blocked - no Rules"), `:505` (TC-141... "Blocked - not Ready"), `:744` (TC-179... "Blocked - no Rules no associated projections"), `:861` (TC-193) are all tagged `@smoke_m2`/`@api` via the shared `test.describe(...)` at line 156, and `.gitlab-ci.yml:203-210`'s existing `api:smoke-m2:mr` job (unchanged by this diff) runs `npx playwright test --project=API-tests --grep @smoke_m2` on every `merge_request_event` whose title doesn't mention health-check/regression/integration/e2e — which this MR's own title does not, so this exact job runs on this MR and on every subsequent MR touching the suite. None of the five use `test.skip`/`test.fixme`. Per `fullstack-aqa-agent.md`'s own principle ("Flaky tests are treated as production incidents: quarantine immediately... never silently re-run until green") and the Full-Stack Automation Coverage Checklist ("No case is marked Automated while its linked test is failing"), shipping known-failing/blocked cases into the merge-blocking smoke gate without quarantine either breaks the gate for an already-tracked defect (TB-1794) or trains reviewers to ignore red smoke runs. Fix: `test.fixme('TC-...', ...)` (with the TB-1794 reference preserved) for the blocked cases until the platform gap closes, or move them out of `@smoke_m2` into a separately tracked suite.

## Possible Risks

**[Possible Risk] Plugin-lifecycle test cases (TC-251/271/293/295) degrade to read-only checks after their first successful run against a persistent environment.** `pluginState.pluginId` is the fixed id `PLUGIN_MANAGER_VALUES.expectedId` (`api/utils/plugin-manager.values.ts:15`), never suffixed per-run; TC-251's Step 1 (`projection-forms-smoke.spec.ts` around the plugin-existence check) returns early without uploading if the plugin already exists, and no test ever deletes it (Plugin Manager's Bruno collection exposes no delete endpoint). Once this plugin exists in a shared QA environment (which it will, after the first green run), every later CI run's TC-251 only exercises the GET/existence branch, never the POST/upload path its own title claims to test ("Create Plugin | POST create Plugin with valid Name and jar file"). Fix: either accept and document this as an intentional "ensure exists" smoke check rather than a create-path check, or add an environment-gated cleanup/reset step.

**[Possible Risk] Upload-status assertion is wider than Bruno's documented contract.** `plugin-manager-api-client.ts`-consuming code in `projection-forms-smoke.spec.ts` (Step 2 of TC-251) asserts `[200, 201]` for a successful plugin upload, but `BrunoApi/proj-bruno-api/collections/Plugin Manager/Plugins/Upload Plugin.yml` documents and exemplifies exactly `200` ("Returns 200 on success"), never 201. Accepting an undocumented alternate status could mask an actual contract/version drift between the real service and its documented contract. Fix: assert `200` only, per the Bruno contract, or update the Bruno doc first if 201 is genuinely also valid and confirmed against the live service.

**[Possible Risk] New top-level `resources/` directory + committed binary JAR fixture is an undocumented structural addition.** `docs/frame-specs/architecture.md`'s documented folder layout lists `test-data/` for payload factories only; this MR introduces `resources/proj-identity-confinement-validation-plugin-1.0.1.jar` (a new binary committed to git, first-ever use of this folder per `git log --diff-filter=A -- 'resources/*'`) with no corresponding update to `architecture.md` or a decision doc, contrary to `rules/definition-of-done.md`'s Documentation checklist ("If an architectural decision was made — a decision doc is created"). Fix: add a short note to `architecture.md` documenting `resources/`'s purpose and update policy for binary test fixtures, or confirm with the team whether this should live outside git entirely (e.g. fetched from an artifact store at test time).

**[Possible Risk] `field-definition-api-client.ts`'s new `getFieldById` has no consumer in this diff.** `field-definition-api-client.ts:10-12` adds `getFieldById`; the endpoint is real (`Bruno: Field Registry/Field Definition/GET field by id.yml`, `GET {{field-registry-url}}/api/v1/fields/:fieldId`), but a repo-wide search of this diff finds zero call sites for it. The endpoint's existence is legitimately cited, but its necessity *for this specific MR* is not established. Fix: either use it in one of this MR's new cases (if a field-lookup assertion was intended somewhere) or defer adding it until a consuming case exists.

## Nice-to-Have Improvements

**[Nice-to-Have] `TC02_PROJECTION_ID`/`TC02_FIELD_IDS` are declared and named for "TC-02" but first populated inside the "TC-48" test.** `projection-forms-smoke.spec.ts:174-175` declares both as top-level `let`s; `TC02_PROJECTION_ID` is first assigned at `:392`, inside `test('TC-48 - ...')`, not `TC-02`, and is then consumed by TC-106/141/179/193. The naming strongly implies TC-02 ownership and is likely a leftover from the case numbers being re-sequenced against the linked Google Sheet. Fix: rename to something ownership-neutral (e.g. `SHARED_PROJECTION_ID`) or align the variable prefix with the test that actually sets it.

**[Nice-to-Have] Two parallel "create/ensure projection definition" code paths now exist across two different client classes.** `SysCoreApiClient.ensureProjectionExists` (`sys-core-api-client.ts:44-99`, pre-existing) and the new `TableRegistryApiClient.inputProjectionDefinition` (`table-registry-api-client.ts:136-145`) both POST to `SYS_CORE_API_PATHS.PROJECTION.DEFINITION_OPERATION`, for different reasons (idempotent precondition setup vs. asserting on the INPUT response contract) — a deliberate and justified distinction today, but worth a one-line doc comment on `inputProjectionDefinition` clarifying when to reach for it over `ensureProjectionExists`, so a future reader doesn't reach for the wrong one.
