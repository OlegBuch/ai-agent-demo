## 1. Контракт `POST currency-engine/api/v1/currencies/rates` — форма меняется, поведение нет

**Прямая цитата разработчика (22:46–23:07), закрывающая тему:** *"Мы имеем вот такой бодик... Он
для вас, по идее, ничего не меняет, просто другое описание. Ну, как бы каждая валюта по
отдельности, базовой, кватируемой. И немножко по-другому рейта. Соответственно, в рейте у нас
именно type рейта и его какое-то value."* — то есть это **чисто изменение формы ответа**, не новая
бизнес-логика (в отличие от §3/§5 ниже, которые меняют поведение).

### Response: было → станет

Текущий (подтверждено `proj-bruno-api` `Currency Engine/Resolve Rate.yml` и
`api/types/currency-engine.types.ts` в `proj-test-automation`):
```json
{"baseCurrency":"USD","quoteCurrency":"EUR","rateType":"MID","quoteCode":1,"rateValue":1.0850}
```

Новый (00:49–01:08, 11:46–12:03, подтверждено дословно примером из задания пользователя):
```json
{
  "baseCurrency": {"currency":"USD","quotationCode":0,"numberOfDecimals":2},
  "quoteCurrency": {"currency":"EUR","quotationCode":0,"numberOfDecimals":2},
  "rate": {"type":"MID","value":{"units":1,"nanos":90000000}}
}
```

Разбор по полям:
- `baseCurrency`/`quoteCurrency` из строк-кодов становятся самоописывающими объектами
  (`currency`+`quotationCode`+`numberOfDecimals`) — разработчик прямо это называет (11:46–12:03):
  *"мы четко описываем базовую валюту с quotation code, number of decimal... Мы прям полностью
  описываем."*
- Отдельное поле `quoteCode` (сейчас — `QUOTATION_CODE` **только** базовой валюты, единственное
  событие которого в текущем контракте — обеспечить FROM-side масштабирование при триангуляции на
  стороне вызывающего, см. [US-01.13.03/README.md](US-01.13.03/README.md)'s "Triangulation
  arithmetic") **пропадает как отдельное поле**, но не пропадает как данные — теперь `quotationCode`
  есть у **обеих** валют внутри их собственных объектов. Функционально это расширение: раньше
  вызывающий мог узнать `QUOTATION_CODE` только базовой стороны, теперь обеих сразу.
  **Открытый вопрос для Bruno/дальнейшей проверки:** нужно ли будет клиенту после апдейта отдельно
  запрашивать `numberOfDecimals`/`quotationCode` цитируемой валюты (сейчас это не нужно вовсе), и
  не появится ли расхождение с уже задокументированным "FROM-side only" правилом округления при
  триангуляции — сама формула не менялась (в звонке никто не говорил про изменение арифметики
  триангуляции), поменялась только упаковка уже существующих чисел.
- `rateType`+`rateValue` (два плоских поля) объединяются в один вложенный `rate: {type, value}` —
  `value` при этом становится `{units, nanos}`, тем же самым Money/Decimal-примитивом, что уже
  используется полем `amount` на запросе (`api/types/charges-calculation-engine.types.ts`'s
  `AmountInput`/`toAmount()`, общий для Charge/Interest/Posting/Balance Engine — подтверждено
  Bruno-грепом, см. §7). Это не новый примитив, а распространение уже принятого паттерна на ещё
  одно поле.
- `amount` на **запросе** не меняется — разработчик сам на секунду засомневался (00:44 *"возможно,
  нет, а стоп, она таки приходила, все хорошо"*) и подтвердил: уже было `{units,nanos}`.

### Request: поле `currencies[]` полностью убирается

13:34–13:48, прямая цитата: *"currencies убирается, вообще этого не будет больше... нет у нас
массива currencies. Будет только базовая [валюта]. И [к]вотируемая, да, всегда она будет."*

Сейчас `ResolveRatePayload.currencies?: string[]` — "array mode" (неупорядоченная пара,
подтверждено `Currency Engine/Resolve Rate (Unordered Pair).yml`, движок сам сортирует по
`BASE_RANK`) — **удаляется целиком**. После апдейта `baseCurrency`+`quoteCurrency` (или сама валюта
у нового endpoint, см. §3) станут обязательными явными полями, второго "неупорядоченного" режима
вызова не будет.

**Прямое следствие для тестов:** `US-01.13.04/README.md`'s замечание про "request mode
(`baseCurrency`/`quoteCurrency` explicit pair for one, `currencies[]` array mode for the other)" как
способ различить два теста на одну и ту же бизнес-проверку **перестанет быть валидным** после
апдейта — `currencies[]`-вариант просто перестанет существовать как способ вызова. Не трогать до
подтверждения на QA (см. §8), но держать в уме при ревью этого файла после деплоя.

## 2. Найденный (не подтверждённый, не исправленный) баг: непоследовательная проверка `END_DATETIME`

09:10–09:16, прямая цитата: *"дата не провидается. Вот первый баг, который я вижу"* — и далее
10:31–10:53: *"end date time, может быть, оно не везде провидается, где-то у меня висит баг."*

Что конкретно наблюдал разработчик: запрос на пару, у которой найденная запись `CURRENCY.RATES`
имела `END_DATETIME` в прошлом (просрочена), тем не менее вернул **живой** курс вместо `404 Rate
Not Found`. Обошёл вживую (не фикс, а ручной воркэраунд для демо) — проставил `END_DATETIME` на
будущее у всех своих тестовых записей вручную.

**Это отдельная, новая находка — не путать с уже задокументированным TB-3132**
([US-01.13.03/README.md](US-01.13.03/README.md)'s "Fifth live run" раздел): TB-3132 — про то, что
*распознанный как просроченный* курс отдаёт `500` вместо `404` (баг в обработке уже
задетектированного истечения). Здесь разработчик описывает нечто раньше в конвейере: сам факт
истечения **не всегда проверяется** — по крайней мере один код-путь пропустил запись, чей
`END_DATETIME` уже прошёл, и вернул её как живую. Он сам называет это "где-то у меня висит баг" —
т.е. подозревает непоследовательность между разными местами, где `END_DATETIME` читается/
фильтруется, а не единственный локализованный дефект.

**Статус: не подтверждено, не тикетировано на момент записи, наблюдение было ad hoc на локальной
машине разработчика (не на QA, где по факту сейчас крутится совсем другой билд).** Не пытаться
воспроизвести/автоматизировать этот кейс до отдельного подтверждения от разработчика — только
занести в бэклог вопросов на понедельник.

## 3. Решение (не баг): одинаковая валюта с обеих сторон → `rate: 1`, без ошибки

18:04–18:47: после самокоррекции живого хода мыслей (изначально разработчик перепутал кейс
"валюта = транзитная валюта" — 17:47–18:04 сам себя поправил: *"я вообще все напутал"* — если
валюта запроса совпадает с транзитной, прямой/локальный/глобальный курс всё равно найдётся, это не
особый случай) команда явно согласовала (18:30–18:47): *"здесь в кейсе SAF на SAF у них rate 1,
потому что это одна и та же валюта. Но мы заалайнили, что мы не [вы]плёвываем здесь ошибку, что мы
прямо говорим, что у нас один rate."*

Важная деталь: эта проверка **не** делается через явное сравнение с `LOCAL_CURRENCY` компании —
вызывающий не обязан знать, что такое локальная валюта компании (18:21–18:30: *"когда мы хотим
какую-то валюту привезти к локальной... не знаем, что у нас SAF локальная... но мы не проверяем.
Тот, кто нам отправляет, не знает"*) — это естественный результат резолва одинаковой пары, а не
специальный guard.

## 5. Изменение `CURRENCY.ORDER~MASTER`: бизнес-юнит становится опциональным (или запрещённым) в зависимости от `DIFF_UNIT` маркета

**Код будет залит в понедельник-вторник** (18:58–19:07) — на момент записи это ещё **не
реализовано**, только согласовано словесно. Правило (19:07–20:47):

- Если у `CURRENCY.MARKET~MASTER` (наши доки называют поле `DIFF_UNIT`, разработчик произносит
  "unit diff false"/"unit-div-false" — соответствует) `DIFF_UNIT = false` → `INPUT` на
  `CURRENCY.ORDER~MASTER` **должен** идти без бизнес-юнита (`UNIT` как `null`/не передан) — тогда
  создаётся один общий рейт-рекорд, который читают все бизнес-юниты компании разом.
- Если при этом `DIFF_UNIT = false`, но бизнес-юнит **всё же передан** — это теперь **ошибка
  пользователя** (запрос отклоняется), потому что вызывающий ошибочно полагает, что для этого
  маркета курсы дифференцируются по юниту, а это не так.
- `RATE_TYPE`, выбранный в этой ситуации (MID/BID/ASK), значения не имеет для самого правила — оно
  чисто про наличие/отсутствие бизнес-юнита, а не про тип курса (20:19–20:27: *"а если мы туда ask
  засунем? Не имеет значения"*).
- Явно отмечено самим разработчиком как ранее не учтённая деталь (20:47–20:54: *"Это мы не учли,
  когда это делали"*), и явно запрошены **новые тест-кейсы** на этот сценарий ("local currency,
  no business unit") — конкретно 2-3 штуки, не полный набор.

**Важно для наших уже написанных тестов:** ни `currency-regression.spec.ts`, ни
`currency-smoke.spec.ts` сейчас не тестируют `CURRENCY.ORDER` с рынком `DIFF_UNIT=false` без
бизнес-юнита — это чистый пробел, который стоит закрыть **после** того как код реально попадёт на
QA (сейчас — предмет для теста, не для немедленной автоматизации per "No automate on contract
mismatch").

## 6. Правило `DIFF_AMT` — переподтверждение уже известного, не новая функциональность

21:04–21:58 сначала звучит как анонс нового ограничения (*"будет ограничение... я не сегодня
расскажу"*), но по факту описывает уже задокументированное в этом модуле поведение (TB-2980, см.
[INDEX.md](INDEX.md)'s Patterns-раздел): при `DIFF_AMT = false` допустима ровно одна полоса
`RATE_BANDS` от `AMT_FROM = 0` ("не должно быть больше одного, currency order будет
[отвер]гать/reject"), при `DIFF_AMT = true` — полосы по сумме, как и раньше. **Никакой новой
механики здесь нет** — это просто объяснение существующего правила в контексте нового
"нацбанк"-маркета (у которого `DIFF_AMT` тоже жёстко `false`, см. §4).
