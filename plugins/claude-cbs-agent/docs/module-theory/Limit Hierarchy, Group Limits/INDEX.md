## Lead company vs company (BA/dev tickets, verbatim where quoted)

- `COMPANY` records: `LEAD_COMPANY` is a LINKED_TABLE to COMPANY. A lead references itself; a branch references its lead. On the environments: MOCK, MOCK_1, BNK, CBS are leads; **BNK-BR is a branch of BNK**; MOCK is a standalone lead.
- Data location (BUSINESS.UNIT spec, page 1693024257): "Physical data lives in the lead company's schema, so a user assigned to a lead can work with a branch company's records and vice versa ... Both sides are therefore resolved through `LEAD_COMPANY` before comparing." So FIN data of a branch is read and written through its lead's schema.
- Limit parameters are lead-level (TB-3653 "Add functional during update lead company limit variables", **To Do**, Artur Fonichkin): "1. If limits are updated for LEAD_COMPANY they have to be updated for all branches 2. Branch company limits can't be updated (LEAD_COMPANY != current company) 3. If branch company created it has to get limits from LEAD_COMPANY" - for `GRP_CREDIT_LIMIT`, `NET_OUTSTANDING`, `ADM_EXTENSION_DAYS` (TB-3570: BOOLEAN false, BOOLEAN false, NUMERIC "0", on `COMPANY` instead of a `LIMIT.PARAMETER` singleton; Bruno `LeadDatesValidator` blocks branch creation without the lead).
- Consequences for tests (inference, not yet confirmed live): the company in `Cbs-User-Context`/`X-Company-Code` should be a **lead**; writing `GRP_CREDIT_LIMIT` on a branch is meant to be rejected, but TB-3653 is not done, so today the cascade/rejection may not exist; test data (references, limits, groups, customers) lands in the lead's schema (`companyScopedSchema`, e.g. `li_limit_mock`).
- The workbook's precondition company is **BNK** (lead, DEFAULT_AUTH false, XAF), which exists on both environments, together with a ready-made branch **BNK-BR** for lead/branch cases. The spec currently uses `COMPANY_CODE` (MOCK). **MOCK has `DEFAULT_AUTH=true`**; what that does to the 4-eyes flow (INPUT landing LIVE without AUTH?) is not yet verified - until it is, the UNAU/LIVE assertions are at risk on MOCK.

## Patterns & Predictive Rules (priors from this analysis; unconfirmed live - update after first live pass)

- **Required-ness is per projection, not per table.** `~MASTER` requires LIMIT_CURRENCY and INTERNAL_AMOUNT; `~INTERNAL` carries the full field set; REFERENCE `~MASTER` requires DESCRIPTION, REDUCING_LIMIT, TIME_BAND. **Predict:** a missing-field negative test must target the right projection.
- **4-eyes differs by projection.** `~MASTER` = INPUT then AUTH by a genuinely different user (see `docs/common-issues/keycloak-and-auth/`); `~INTERNAL` and COMPANY land LIVE. **Predict:** fixtures that need TOTAL_OS or ACCOUNTS must go through `~INTERNAL`; every `~MASTER` setup needs the AUTH step, and AUTH can reject what INPUT accepted (workbook NR-05/PR-13 re-check at AUTH).
- **Ancestors appear asynchronously.** Auto-creation is a Kafka-fed plugin; **predict** any assertion on ancestors needs a poll (workbook: SEE up to 30 s), and any test that asserts "nothing created" needs a bounded wait, not an immediate read. Amendments raise no `RECORD_CREATED`, so links are not re-established (workbook Q12).
- **Cross-record invariants live in plugins, not schema.** Owner xor, same-owner parent, cycle, one-limit-per-node, one-group-per-customer, account rules. **Predict:** status is 400 or 422 depending on the class (workbook accepts both in Bruno flows); do not hardcode a status until live-confirmed, and then assert exactly one (see `feedback_always-one-expected-status`).
- **Uniqueness-constrained business ids.** `LiabilityNo.LimitRef.Seq` and "one limit per node per owner" collide across runs. **Predict:** one fresh customer per test (workbook convention `LI.CUS.<TC-ID>`) and dynamic ids; fixed ids like 9103.10000.1 or 10000/1000/1010 are examples, not mandatory.
- **Stories describe more than the build for runtime behaviour.** Everything that needs a draw/evaluate call (roll-up, release, restriction principle, concurrency) is the uncovered area. **Predict:** each new Story in this epic that names `/limits/evaluate` is blocked until the engine contract is in Bruno.
- **Messages and error ids: the Story says one thing, the build another** (3 of 4 Stories). Treat the Story text as the expected value and escalate the mismatch; do not silently assert the Bruno id.

- **Group setup order is fixed (confirmed 2026-10-01 by devs).** Empty `LI.LIMIT.SHARING.GROUP` -> group limit (`GROUP_ID`) -> a LIVE limit per customer with the **same `LIMIT_REFERENCE_ID`** -> add customers (amend + AUTH). **Predict:** any group test that submits members at creation, or customers without a matching limit, fails; and adding a member checks `sum(TOTAL_OS of all members) <= group ADVISED_AMOUNT`.
- **Accounts are never added by a user directly.** Only a contract operation whose conditions carry class attribute = Limit links an account (bilateral, via plugins); `~INTERNAL` is the plugins' write path. **Predict:** any account-attach TC written as a direct `~INTERNAL` write (PR-21/22, NR-17) is suspect until reworked as a contract flow (US-09.01.03 SM-05).
- **COMPANY limit settings (`GRP_CREDIT_LIMIT`, `ADM_EXTENSION_DAYS`, `NET_OUTSTANDING`) are Lead-company-only**; netting TCs additionally need `NET_OUTSTANDING = true`. **Predict:** fixtures must pick the Lead company (BNK), not a branch.
- **Plugin rejections are HTTP 400 today; error ids/messages are not final** (backfill after the manual review ends). **Predict:** assert status only, not message/id, until the backfill lands.
- **Every concurrency/parallel TC is blocked until atomicity ships (confirmed 2026-10-05, "not started").** **Predict:** a parallel-write test passes for the wrong reason today (last write overwrites silently); mark Not Automatable, never assert "one of two wins".
- **Multi-violation negatives return one error, no aggregation (2026-10-05).** **Predict:** assert status 400 only; the winning error depends on check order inside the plugin.
- **Plugin-guarded writes have two modes: QA-open and sealed.** `LI.LIMIT~INTERNAL` account writes are open for QA now and will be closed by a rejecting plugin. **Predict:** a test built on a direct `~INTERNAL` account write dies when the plugin lands; the durable path is the contract operation.
- **Group member checks are by reference hierarchy, per level, at LIVE not NAU (2026-10-05).** Customer needs all group references; debt adds per level once; NAU drafts never lock a customer or block the `GRP_CREDIT_LIMIT` switch-off; conflicts surface at AUTH. **Predict:** capacity/one-group failures appear at AUTH, not INPUT, when state changed in between.
- **Stories describe checks the build lacks (inactive customer, one group per customer).** **Predict:** a "negative" case for a Story rule may return 200 today; classify as bug/expected-failure, don't weaken the assertion.
- **Review decisions lag the workbook.** V2 applied 9 of the dozens of 2026-10-01 decisions; **predict** every automation start must diff the workbook against the latest call digest, not trust the sheet alone.
- **`LI.LIMIT~INTERNAL` INPUT replaces the whole record, a partial payload wipes it (live-confirmed 2026-10-08, bankuat run vm-results-api-20261008-114204).** An `{ACCOUNTS:[..]}`-only INPUT returns and then SEEs `data` with only `ACCOUNTS`; the next write then fails `LIMIT_REFERENCES_CANNOT_BE_CHANGED_AFTER_CREATION` (full payload) or `ACCOUNTS_CAN_ONLY_BE_ATTACHED_TO_A_CUSTOMER_LIMIT` (partial). **Predict:** every `~INTERNAL` write that must keep the record must resend the full body (as the create does); a precondition that attaches the first account with `buildAccountAttachPayload` breaks any second write.
- **The Limit event topic only ever carries `RECORD_CREATED` (verified on bankuat Kafka 2026-10-08).** No `RECORD_UPDATED`/`LIMIT.HIERARCHY.UPDATED` exists on `two.LI.LIMIT`, and Bruno seeding sets `RECORD_UPDATED.enabled=false` for LI.LIMIT (`09 - Enable Event Emission/01`); a failing consumer plugin lands in `events.<env>.LI.LIMIT.<env>.LI.LIMIT.<env>.LI.LIMIT.dlq` with the error in header `kafka_dlt-exception-message`. **Predict:** every "one RECORD_UPDATED" step reds, every "no event" step passes vacuously; and when an async plugin result never shows up in SEE, read that DLQ before suspecting the test.
- **Payload vs check (owner rule 2026-10-08).** A TC may be wrong about a request body, then follow Bruno / the real contract; a TC check (code, message, event) is asserted verbatim and a mismatch is escalated with its owner. **Predict:** adapting a check to the observed behaviour is the one move the owner rejects.
