# TC-04 NAU-staging fix (Safe Deletion Policy — DEL segment purge blocking)

**Date/time:** 2026-08-03 20:39 · **Branch:** group-3/TB-2102-newTests · **Ticket(s):** TB-2102 (branch), related: TB-626

## Discussed
- User asked why TC-04 (`customization-regression.spec.ts`, "Safe Deletion Policy — DEL segment
  purge blocking") started failing on `403 User does not have access to table`, after previously
  passing.
- Root-caused: a fixed 10s sleep in `setupFinTableWithFourEyes` assumed the MAKER's group
  PERMISSIONS grant (RBAC via Kafka security-event replay) would propagate quickly. This stopped
  being enough once the test suite's `Implemented multi-describes depends on stories` /
  `Fix describe` restructuring added far more table/group setup traffic ahead of this describe
  block in the same run. User asked for a proper poll: 300s max wait, 30s interval, instead of the
  blind sleep.
- After that fix, hit a new, then-reproducible error: `DELETE` returning `400` ("DELETE operation
  cannot be performed for record id=X, seqNo=1"). Live DB inspection (throwaway repro spec, deleted
  after use) showed the record landing straight in `LIV` with status `LIVE` instead of `NAU` —
  i.e. `INPUT` was bypassing four-eyes staging entirely.
- Checked Jira TB-626 (bank-proj) — related in spirit (record routed to LIV instead of NAU) but not
  the same precondition (that ticket is about NAU being *absent* from `spaces`; here NAU was
  present and INPUT still bypassed it).
- Dev (Ilya Vatsevich) confirmed directly: a projection's `authOperationRequired` flag (colloquially
  "isAuthRequired") defaults to `false`; must be `true` for INPUT to stage into NAU instead of
  routing straight to LIV as already-authorized.
- Found a working reference: a local, non-exported `setAuthRequired` function inside
  `audit-fields-regression.spec.ts`. Initially extracted it into a shared, exported
  `setAuthRequired` in `table-registry-helper.ts` and made `audit-fields-regression.spec.ts`
  delegate to it — user reverted that file back to its original state ("это не наши тесты, не хочу
  их сломать") and asked to keep the fix scoped to `table-registry-helper.ts` +
  `customization-regression.spec.ts` only, not touching the other two spec files that also call
  the shared `setupFinTableWithFourEyes` (`table-registry-regression.spec.ts`,
  `table-registry-smoke.spec.ts`).
- Several live-environment repro attempts (each 2–7 min: table creation, pod warm-up, dozens of
  retries) surfaced a chain of payload-shape bugs inherited from the copied fallback branch: wrong
  field name (`description` instead of `name`), and an invalid projection id (bare `tableId` is
  rejected by the backend — must be `{tableId}~NAME`). Consulted the Bruno collection
  (`C:\Users\user\BrunoApi\proj-bruno-api`) for real "Create X projection" examples to confirm the
  correct payload shape/endpoint/field names and the `{tableId}~NAME` id convention, instead of
  continuing to guess via live trial-and-error.
- Final design, confirmed working (user ran TC-04 themselves — passed): a new opt-in
  `enableFourEyesAuth()` helper, called explicitly only from
  `customization-regression.spec.ts`'s DEL-purge describe block.

  `MAKER_AUTHORIZATION_POLL_INTERVAL_MS` (30_000).
- `api/system_core/helpers/table-registry-helper.ts`:
  - `waitForMakerAuthorized()` — polls a disposable probe INPUT/DELETE via the MAKER's
    `inputterClient` until it stops returning 403, replacing the old blind
    `setTimeout(resolve, 10000)` in `setupFinTableWithFourEyes`.
  - Exported `setAuthRequired(client, projectionId, required, customHeaders?, fallbackSchema?)` —
    GETs the current projection definition (`SYS_CORE_API_PATHS.PROJECTION.DEFINITIONS`), toggles
    `authOperationRequired`, POSTs the update (`DEFINITION_OPERATION(tableId, 'INPUT')`); the
    fallback/create payload shape now matches the real Bruno examples (`name`, not `description`;
    accepts 200/201/202/409).
  - Exported `enableFourEyesAuth(adminClient, tableId, schema, customHeaders?)` — ensures a
    `{tableId}~AUTO.TEST` projection exists with `authOperationRequired: true`; returns the
    projection id to use for record operations in place of the bare table id.

    definition), purely additive — so a caller can pass it to `enableFourEyesAuth` without
    duplicating the schema literal. No other behavior change to this shared function; it's still
    used unmodified by `table-registry-regression.spec.ts` and `table-registry-smoke.spec.ts`.

## Learned
- A projection id must start with `{tableId}~` — a bare tableId is rejected by the table-registry
  backend with `400: "Projection ID must start with table ID prefix '...~'"`. Record operations
  (`POST .../projections/{id}/records/operations/{op}`) tolerate a bare tableId as an implicit
  default projection; the projection-*definition management* endpoint
  (`.../tables/{tableId}/definitions/projections...`) does not.
- `authOperationRequired` on a projection controls whether `INPUT` stages into `NAU` (`true`) or
  routes straight to `LIV` as already-authorized (`false`, the default) — confirmed by the dev and
  by the Bruno collection (Product Factory seeding docs: "the default Projection's
  isAuthRequired=true would block INPUT (no NAU space)").
- The real payload for creating/updating a projection definition
  (`POST .../definitions/projections/operation/INPUT`) uses `name` (not `description`) and accepts
  `200/201/202/409` as success — confirmed against multiple real Bruno seed-request examples
  (e.g. `AM.POSTING.RESTRICT~INPUT`, `CUSTOMER~SIMPLE`, `PF.ATTRIBUTE~MAIN`).
- A local, non-exported `setAuthRequired` in `audit-fields-regression.spec.ts` had a broken
  fallback/create branch that was never actually exercised by that file's passing tests (they
  always pre-create their projection first via `SystemCoreProjectionHelper.createProjection`, so
  the GET-then-update path is the only one ever hit). Copying "proven" code without confirming the
  *specific branch* is actually exercised can silently inherit a latent bug — captured as memory
  `feedback_verify-api-contract-before-live-trial` (see also
  `feedback_justify-additions-before-making`).
- Jira TB-626 (bank-proj, "[Table Registry][FIN] Record is added to LIV space instead of error in
  case NAU space is not configured") is related in spirit but not the same precondition as this
  session's bug — status "Code Review" as of its last comment (2026-06-18).
- When a shared helper (`setupFinTableWithFourEyes`) is used by multiple spec files, the user
  wants new/risky behavior added as an explicit opt-in call from only the spec file that needs
  it, rather than baked into the shared function's default behavior — ask before widening blast
  radius on a shared helper used by files outside the current task's scope.
