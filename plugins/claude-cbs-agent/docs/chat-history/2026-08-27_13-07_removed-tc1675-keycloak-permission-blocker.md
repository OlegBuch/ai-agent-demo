# Removed TC-1675 (Password Policy → Keycloak realm sync) — blocked by Keycloak service-account permissions

## Context

TB-3196 (Access Administration smoke suite, `api/security_management/tests/access-administration-smoke.spec.ts`).
While implementing `US-02.03.01 | Password Governance Configuration`, TC-1606 (Add Password Policy
happy path) was implemented and confirmed passing. TC-1675 ("Password Policy configured via
SYSTEM.PARAMETER is synced to the Keycloak realm password policy") was implemented next, per manual
QA ticket #1675, to verify the `SmsPolicySyncHook` actually pushes the CBS-side Password Policy into
Keycloak's realm `passwordPolicy` string.

## Why it was removed

Diagnostic logging (added specifically for this investigation, see below) proved conclusively that
`GET admin/realms/{realm}` — called via the test suite's Keycloak service account
(`KEYCLOAK_ADMIN_CLIENT_ID`/`KEYCLOAK_CLIENT_SECRET`, `client_credentials` grant) — returns a
**truncated** `RealmRepresentation` containing only 4 fields:

```json
{
  "realm": "proj-qa",
  "registrationEmailAsUsername": false,
  "bruteForceProtected": true,
  "supportedLocales": []
}
```

A real Keycloak `RealmRepresentation` has 50+ fields (including `passwordPolicy`, `failureFactor`,
`ssoSessionIdleTimeout`). The fact that `ssoSessionIdleTimeout` — a field Keycloak always returns
with a default value for any realm — is completely absent (not `undefined`-via-missing-key sometimes,
literally never present across 13 consecutive polls spanning 15s) rules out a timing/propagation race.
It points at a **permission scope issue**: the service account most likely has `manage-users`
(sufficient for `createUser`/`resetPassword`/`getUserById`, all of which work fine and are used by
TC-1514/TC-1521) but lacks `view-realm` (or `manage-realm`) from the `realm-management` client, so
Keycloak silently returns a reduced representation instead of a 403.

This was confirmed to be a stable, reproducible blocker (not a flake) across three separate live runs
on 2026-08-27, all producing the identical 4-key response.

## What was tried before removing

1. **Polling** — added a 15s/1s poll (`pollUntilReady`) on `GET admin/realms/{realm}` on the
   assumption the hook might be async. No improvement; the response never changed shape across 13
   attempts.
2. **HTTP exchange logging** — temporarily added general-purpose request/response logging to
   `api/utils/services/base-api-client.ts` (`get`/`post`/`put`/`patch`/`delete`), writing to both the
   terminal and a timestamped file under `LOG/api-client-<ISO-timestamp>.log`, matching this repo's
   pre-existing `LOG/` convention (already gitignored). This surfaced the 4-key evidence below. It was
   removed again afterward (see "What was removed" — this was diagnostic-only, not kept).
3. **One-shot diagnostic** — logged `Object.keys(response.body)` once per test run to see exactly
   which fields Keycloak actually returns. This produced the 4-key evidence above.

None of this is a code-side fix — the blocker is Keycloak IAM configuration outside this repo.

## What was removed from the test file

- The TC-1675 `test(...)` block itself (STEP 1: INPUT SYSTEM.PARAMETER with a distinctive Password
  Policy; STEP 2: poll `GET admin/realms/{realm}` for the synced `passwordPolicy` string).
- The now-unused `pollUntilReady` import (only consumer was TC-1675).
- `KeycloakAdminApiClient.getRealm()` (`api/utils/services/keycloak-admin-api-client.ts`) — the
  `GET admin/realms/{realm}` method added specifically to support this test. Left no other callers
  after TC-1675's removal.

`US-02.03.01 | Password Governance Configuration` now contains only TC-1606.

## What was also removed: the diagnostic HTTP logging

The `[HTTP]` request/response logging added to `base-api-client.ts` (`get`/`post`/`put`/`patch`/
`delete`, writing to terminal + `LOG/api-client-<ISO-timestamp>.log`) was diagnostic-only, added
specifically to investigate this blocker. Once the investigation concluded, it was reverted in full:

- `base-api-client.ts` restored to its pre-investigation state — no `fs`/`path` imports, no
  `HTTP_LOG_DIR`/`HTTP_LOG_FILE_PATH` constants, no `formatLogBody`/`writeHttpLog`/`logHttpRequest`/
  `logHttpResponse` helpers, and the five HTTP methods (`post`/`get`/`put`/`patch`/`delete`) back to
  their original one-line `fn` closures (no `logHttpRequest`/`logHttpResponse` calls).
- The `LOG/*.log` files generated by this session's own runs (2026-08-27) were deleted; pre-existing
  files from earlier sessions (2026-08-22 through 2026-08-24) were left untouched.
- `.gitignore` was not changed either way — `LOG/` was already gitignored before this investigation
  started, nothing to revert there.

If general-purpose HTTP exchange logging is wanted again in the future (it did prove useful for
diagnosing this exact class of problem), it would need to be re-added from scratch — nothing from it
was kept.

## What stays (not removed)

- **TC-1606** (`Add Password Policy happy path`) — unaffected, still passing.
- **`access-administration-helper.ts`, `ACCESS_ADMINISTRATION_CONSTS`** — unaffected; these back
  TC-1514 (`PASSWORD.RESET`) and TC-1521 (`SIGN.ON.RESET`), which have no dependency on TC-1675's code
  path and remain green.

## How to restore this test later

Once the Keycloak service account is granted `view-realm` (or `manage-realm`) on `realm-management`
in the target realm:

1. Re-add `getRealm()` to `KeycloakAdminApiClient`:
   ```typescript
   async getRealm(): Promise<APIResponse> {
     return this.get(this.basePath);
   }
   ```
2. Re-add the TC-1675 test to `US-02.03.01 | Password Governance Configuration` in
   `access-administration-smoke.spec.ts` (full source below), verify with a live run — the 15s/1s poll
   on `passwordPolicy` should very plausibly no longer be necessary once permissions are fixed (it was
   only added on the hypothesis the failure was timing-related, which this investigation disproved) —
   worth trying a single `GET` first before re-adding the poll wrapper.

<summary>Full TC-1675 source (as last implemented, before removal)</summary>

```typescript
import { resolveKeycloakContext } from '../../utils/services/auth-service';
import { pollUntilReady } from '../../utils/helpers/test-polling-helper';

test(
  'TC-1675: Password Policy configured via SYSTEM.PARAMETER is synced to the Keycloak realm password policy (API)',
  allureCaseId(1675),
  async ({ authenticatedApiContext, playwright }) => {
    const client = new TableRegistryApiClient(authenticatedApiContext);
    const policyOverrides = {
      PWD_MIN_LENGTH: '18',
      PWD_COMPLEXITY: { upperCase: 3, lowerCase: 4, digits: 5, specialChars: 6 },
      PWD_EXPIRY_DAYS: '45',
      PWD_HISTORY_DEPTH: '1',
      MAX_FAILED_ATTEMPTS: '9',
      AUTOLOG_TIME_MINS: '19',
      SESSION_TIMEOUT: '31',
    };

    await test.step('STEP 1: INPUT SYSTEM.PARAMETER (id=SYSTEM) with a distinctive Password Policy — accepted', async () => {
      const result = await inputSystemParameterWithState(client, policyOverrides);
      expect(
        result.inputResult.status,
        `Expected Password Policy INPUT to return 200, got ${result.inputResult.status}: ${result.inputResult.errorMessage}`,
      ).toBe(HTTP_STATUS.OK);
    });

    await test.step('STEP 2: GET the Keycloak realm representation — passwordPolicy reflects the submitted values (polling for the async SmsPolicySyncHook)', async () => {
      const { requestContext, realm } = await resolveKeycloakContext(playwright.request, {});
      try {
        const kcAdminClient = new KeycloakAdminApiClient(requestContext, realm);
        const expectedTokens = [
          'length(18)',
          'passwordHistory(1)',
          'forceExpiredPasswordChange(45)',
          'upperCase(3)',
          'lowerCase(4)',
          'digits(5)',
          'specialChars(6)',
        ];
        let passwordPolicy = '';

        await pollUntilReady(
          async () => {
            const res = await kcAdminClient.getRealm();
            if (res.status() !== HTTP_STATUS.OK) {
              return { ready: false, diagnostic: `GET realm returned ${res.status()}` };
            }
            const body = (await res.json()) as { passwordPolicy?: string };
            passwordPolicy = body.passwordPolicy ?? '';
            const ready = expectedTokens.every((token) => passwordPolicy.includes(token));
            return { ready, diagnostic: `passwordPolicy so far: "${passwordPolicy}"` };
          },
          15000,
          (lastDiagnostic) =>
            new Error(
              `Timeout waiting for SmsPolicySyncHook to sync the Password Policy to Keycloak realm "${realm}". ${lastDiagnostic ?? ''}`,
            ),
          1000,
        );

        for (const token of expectedTokens) {
          expect(
            passwordPolicy,
            `Expected Keycloak realm passwordPolicy to contain "${token}", got: "${passwordPolicy}"`,
          ).toContain(token);
        }
      } finally {
        await requestContext.dispose();
      }
    });
  },
);
```

## Action item outside this repo — resolved as permanently declined (2026-08-28)

Asked whoever administers the QA Keycloak realm (`proj-qa`) to grant the service account behind
`KEYCLOAK_ADMIN_CLIENT_ID` the `view-realm` client role from `realm-management`. **Answer: this
access cannot be granted.** This is not a temporary/pending blocker anymore — TC-1675 (this test),
plus the Keycloak-sync verification step in TC-1633/TC-1637
(`api/security_management/tests/access-administration-regression.spec.ts`), are permanently out of
scope for this suite via the admin Realm Representation endpoint. The "How to restore this test
later" section above no longer applies as written.

If Keycloak-side password-policy verification is wanted again in the future, it would need a
different mechanism than `GET admin/realms/{realm}` entirely — e.g. behaviorally testing policy
enforcement (attempt a password reset/change that violates the configured policy and confirm
Keycloak rejects it) rather than reading the realm's `passwordPolicy` string directly. Not
investigated or attempted — flagged here only as a possible future direction, not a validated path
(unclear whether the *admin* reset-password endpoint, the only write path this suite currently uses,
even enforces the policy the same way an end-user self-service change would; see also
`docs/chat-history/2026-08-27_15-50_tc1638-1639-skipped-self-service-password-gap.md`, point 2).
