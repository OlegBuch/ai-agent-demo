## Implemented

- **`api/system_core/payload-builder-enquiry.ts`**: `buildProjectionDrilldown` rewritten from a
  standalone literal to a one-line delegation:
  ```typescript
  export function buildProjectionDrilldown(
    projectionId: string,
    label: LocalizedText,
  ): EnquiryDrilldown {
    return buildProjectionDrilldownWithOperations(projectionId, [{ operation: 'SEE', label }]);
  }
  ```
  Signature unchanged; all existing call sites (`enquiry-smoke.spec.ts` TC-754/TC-866/TC-900/
  TC-976, `enquiry-regression.spec.ts`) untouched. Verified via prettier/eslint/tsc/
  `playwright test --list` (92 tests across `enquiry-regression.spec.ts` +
  `enquiry-smoke.spec.ts`, unchanged count). Best single live-verification candidate identified:
  **TC-636** (`enquiry-smoke.spec.ts`) — it both builds a drilldown with `buildProjectionDrilldown`
  on INPUT and asserts the persisted result with `toEqual(buildProjectionDrilldown(...))` on SEE,

## Learned

- **Local Windows Playwright browser validation is unrelated to this repo's actual test needs.**
  `npx playwright install` (bare, no args) tries to install the full default bundle (chromium,
  firefox, **webkit**) and can fail on missing Windows DLLs (`libxml2.dll`, `libsharpyuv.dll`,
  `sqlite3.dll`) for webkit specifically. `playwright.config.ts` only declares two projects,
  `UI-Chromium` (`devices['Desktop Chrome']`) and `API-tests` (`use: {}`, no browser at all) —
  webkit is never used anywhere in this repo. Fix: `npx playwright install chromium`, not the bare
  command.
- **GitLab "Pipeline cannot be run." with no detail, when submitting a manual web-triggered
  pipeline with `TEST_TYPE`/`ENV_TARGET` set** — `.gitlab-ci.yml`'s `workflow:` rules and the
  `api:regression-m2` job's own `rules:` were checked and both should legitimately produce a
  non-empty pipeline for a web-sourced trigger with `TEST_TYPE=regression-m2`. No YAML syntax
  issue found either (the `!reference` tag is valid GitLab CI syntax, just unsupported by a plain
  PyYAML parse — a false alarm from my own check, not a real error). Most likely explanation
  identified (not confirmed — no GitLab access from this environment): the project's
  **Settings → CI/CD → Variables → "Limit which roles can set pipeline variables"** restriction —
  the Run Pipeline form's `TEST_TYPE`/`ENV_TARGET` fields count as setting pipeline variables, and
  GitLab blocks this silently with exactly this banner if the current user's role is below the
  configured threshold. Not something I can fix from this environment; flagged for the user to
  check with a project admin.
- **README/`​.gitlab-ci.yml` documentation drift found (not fixed, not requested):** README's
  "Manual Pipeline Triggers" section describes `TEST_TYPE=all` as the default and a valid option;
  the actual `.gitlab-ci.yml` `TEST_TYPE` variable has no `all` option at all, and its real default
  is `health-check`. Unrelated to any failure seen this session — noted here in case it's worth a
  follow-up doc fix later.
- **Live full-suite run (85 tests) result: 83 passed, 2 failed — neither failure caused by this
  session's refactors.** Confirmed by reading both failing tests' source: neither TC-1014 nor
  TC-1024 references `seedRelatedNameRecord`, `waitForEnquirySelectionFieldReady`,
  `buildProjectionDrilldown`, or `buildProjectionDrilldownWithOperations`.
  - **TC-1014** failed with the exact `ENQUIRY_REGISTRY` propagation-race error signature seen
    before (`target table='ENQUIRY_REGISTRY' does not contain record with ID=... in LIV space`) —
    root cause: this specific test never got the `waitForEnquiryInRegistry` fix that its siblings
    (TC-1010/1018/1800/1723/1029/1015) already had. Pure omission, now fixed (see Implemented).
  - **TC-1024** failed with `Test timeout of 150000ms exceeded`, preceded by
    `[table-registry-helper] Still waiting for table ... 61s/150s elapsed ... 503 — no healthy
    upstream` — the same table-registry-pod-not-ready infra class as TC-1010's earlier
    investigation (see `docs/chat-history/2026-08-26_13-34_tb-2437-2440-inputfieldids-pagination-fixes.md`).
    `createTableAndWait` alone consumed most of the 150s test budget, leaving none for the rest of
    the test (Enquiry/projection/record setup, report generation poll, PDF download). **This is
    live evidence against reducing any of the 12 extended timeouts** — if anything it argues
    150000ms is already tight under a slow-pod scenario, reinforcing (by analogy) that TC-1013's
    larger 700000ms buffer is reasonable rather than excessive. No timeout was changed as a result
    (explicit user decision, both for comment 2's timeout risk and for TC-1014's own timeout).
  - TC-1016 logged (did not fail on) the same known list-scoping platform-behavior note documented
    under task "Soften TC-1016 list-scoping assertion" from an earlier session — expected, not a
    regression.
