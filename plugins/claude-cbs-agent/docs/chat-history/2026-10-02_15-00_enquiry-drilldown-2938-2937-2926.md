## Learned

- **Confirmed product bug, broader than first thought**
  (`proj-ai-agentic/plugins/claude-proj-agent/docs/module-theory/Enquiry and Reporting
  Framework/US-01.07.02/bug-enquiry-type-drilldown-table-field-corrupted-after-save.md`, updated
  this session): a `Type = "Enquiry"` drill-down link's own "Table" field always displays the
  linked Enquiry's id instead of the Table's id, with "Enquiry / Projection" showing a permanent
  "Must be a valid Enquiry" error - confirmed via DevTools Network tab (`GET .../tables/{enquiryId}`
  404s). Originally found while live-building TC-2938 (looked like a save-flow bug at first);
  TC-2937 then proved it reproduces identically for a link seeded directly via the API that never
  touched the UI's own save form, which rules out "corruption introduced by saving" entirely - it's
  a read/render issue for this link Type, full stop. Also confirmed: "Filter Field"/"Operation"
  never render in the UI for `Type = "Enquiry"` at all (fresh or pre-saved), contrary to both
  TC-2938's and TC-2937's own ticket wording (which describe it as "disabled/greyed out", not
  absent). `Type = "Projection"` links are confirmed unaffected by any of this - they display and
  persist correctly.
- **Drill-down link field DOM structure** (`enquiry-drilldown-step-page.ts`): every link row is an
  `<article>` inside `[data-testid="drill-down-step"]`; most of its fields carry
  `name="drilldowns.{rowIndex}.{field}"` (`type`, `targetTableId`, `targetId`, `sourceFieldId`,
  `label.{languageCode}`) - "Operation" and "Order" are the two exceptions with no `name`
  attribute, staying scoped via their own `.ant-form-item-row` label text instead. Label
  (EN-GB) auto-fills from the chosen Enquiry/Projection's own name; a secondary language (FR-FR)
  never auto-fills and must be set manually, for either link Type.
- **An Enquiry's real/composite id depends entirely on how it was created** - a UI-wizard-created
  Enquiry gets `{tableId}~{typedId}` auto-prefixed by the app itself; an Enquiry created directly
  via the API keeps whatever raw `id` the payload set, with no prefix added at all. `gotoEdit()`
  was refactored mid-session to take the real composite id as a parameter rather than assuming
  the prefix, after this exact mismatch caused a `View {tableId}~{enquiryId}` button-not-found
  timeout for an API-seeded Enquiry (TC-2937's first failed run).
- **Group/array multifield table-field shape, and a newly-found variant**: `type: 'array'` +
  `'x-group-type': 'multi'` + `items: {type: 'object', properties: {...}}` is this repo's
  one confirmed shape for a field with real sub-fields (the existing `CHARGES`/`CHARGE_AMOUNT`
  pattern). Newly confirmed this session: a SCALAR multi-value field (no sub-object) needs the
  array's own top-level `x-type`/`x-config` in addition to (not instead of) `items`'s own
  `x-type`/`x-config` - the Table Definition API 400s with `"$.properties.FIELD_E.x-type must be
  a string, $.properties.FIELD_E.x-config must be an object"` otherwise, even though the
  object-items (`CHARGES`-style) shape never needed a top-level `x-type` at all.
- **Enquiry Designer canvas uses the same dnd-kit sortable pattern as Drill-down's own row drag
  handles** (`aria-roledescription="sortable"`, `DndDescribedBy-N` keyboard-instructions live
  region) - confirmed live via outerHTML for a canvas column
  (`[data-testid="enquiry-column-{fieldId}"]`, containing `Configure {fieldId}`/
  `Move {fieldId}` (the drag handle)/`Remove {fieldId}` buttons plus the field's own `<strong>`
  label). This is the first time this repo has a confirmed drag-and-drop target to actually
  automate (prior sightings of the same pattern, on Drill-down rows, never needed reordering
  tested). Not yet confirmed: whether the keyboard Space/ArrowLeft/Space sequence actually
  performs the move (session ended before this could be verified live).
- **`EnquiryDesignerPage`'s Available-Fields locators are reusable against the EDIT page's
  Designer TAB, not just the create wizard's Designer STEP** - confirmed live this session
  (previously only ever driven against the wizard). The separate "Virtual Fields" collapse panel
  (sibling to the regular "Available Fields" panel, not nested inside it) uses the identical
  `Add {fieldLabel}` aria-label pattern as regular fields, so the existing `addField()` method
  works unchanged for adding a virtual field to the canvas too.
- Reconfirmed the already-known **table-registry indexing lag flake** (`waitForEnquiryInRegistry`
  timing out once, passing on an immediate retry) - not investigated further, matches prior
  sessions' notes on this.

  `test.skip` (Jira TB-2994: "global uniqueness") was therefore a permission artefact.
