# AI QA accelerator: review and development priorities

This is an architecture and workflow review of the supplied snapshots. The documented framework validator was run; application workflows were not run because the target applications, environments and service access were unavailable. Operational results and adoption outside these repositories remain unverified. Recommendations below describe proposed work.

## Assessment

The repositories provide a useful foundation for an AI-assisted QA department. ai-agent-demo packages requirements analysis, test-case management, automation and review into a versioned Claude Code plugin. qa-web-mobile-ai-agent contributes reusable QA roles, project profiles, web/mobile exploration and stack adapters. Their strongest features are explicit approval points, traceability from requirements to cases, evidence-based locator discovery, and a rule that unavailable verification must not be reported as a pass.

The next development goal should be a **repeatable, measurable story-to-verdict workflow**. Reliable acceptance decisions, review evidence and controlled execution would make this foundation valuable to a team of roughly 20 engineers. Adding more personas is a lower priority.

## Proposed development sequence

The stages are ordered by dependency. Acceptance conditions are proposed pilot gates, to be agreed with QA and product owners. Human effort refers to review and reference preparation rather than person-days.

| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |

Run status and acceptance verdict should be separate: an infrastructure failure makes the run invalid and affected criteria needs-human; it must not become a product pass. Retries retain the initial failure. Changes to tests after a failure remain visible and reviewed.

For measurement, record human working minutes, agent elapsed time and QA queue time separately. Jira time in status can measure lead time, but does not by itself establish manual effort saved. Start with 10–20 representative stories for calibration; that sample is not enough to establish a rare-defect safety rate. Include blocked runs and the cost of retries and review. Define "autonomy" as completion without unplanned intervention, reporting required approval separately.

The proposed split is a shared workflow contract, reusable execution/stack packs, private project context, and marketplace distribution. Physical repository consolidation can follow a successful pilot. Programmatic execution must load the agreed framework and policies, with this verified in the pilot. Evaluate task outcomes and agent behaviour together, using deterministic checks where possible and calibrated human/model review where needed; see [Anthropic's agent evaluation guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).

The most useful next demonstration is one story processed from intake through a reviewed verdict, including a known defect and an unavailable-environment case. That would make both the current strengths and the route to controlled autonomy concrete.
